# 协议 v1.1（依赖内核 v1.0）

> **一句话**：协议 = 约定「树怎么组织、怎么存」；内核只定义节点本身（四属性 + 7 大类）。
> 同一份数据可以有不同的组织方式，所以协议可以扩展、可以替换。
> **读法**：每条协议都先给一句大白话「它解决什么问题」，再给具体规则——不要求读者懂技术。

## 已登记协议

### shard-v1：分片词库

**一句话**：把一个很大的文件拆成「一个目录 + 很多小分片文件 + 一份清单」；改一个词只动一个小文件，不用重写整个大文件。

**它解决什么**：大文件每次改动都要整份重写，又慢又费硬盘；拆小之后，只重写被改到的那一小片。

| 项 | 说明 |
|----|------|
| 存储形态 | 词库集合 = 一个目录 + 若干可独立打开的分片 `.xirang` + 一份 `manifest.xirang`（清单）。每个分片单独就是一棵可读的树 |
| 怎么切分片 | 由「分片根判定器」决定哪些节点是分片的根：`root`（顶层根，默认）/ `name:<名>` / `depth:<层号>` / `marker:<标记>`；选定根之后，它下面的**整棵子树**都归入同一分片 |
| 怎么写 | 只往目标分片**末尾追加**一条「同一编号的新记录」（后写覆盖）；读 = 按追加顺序取每个编号的最后一条，就是当前视图 |
| 怎么删 | 删 = 追加一条同编号、名字与值都为空的记录（留空槽位）；整条删除 = 删掉那个分片文件 + 清单里的登记 |
| 合并 | 追加会越积越多；用 `xr compact` 把「同一编号只留最后一条」折叠回基版（可手动，也可设阈值自动） |
| 清单长什么样 | `manifest.xirang` 的根节点名是 `分片清单`（普通名字，不是 `@` 辅助节点），挂 `@protocol` 与 `@rule`；分片条目统一挂在 `分片` 容器下（名 = 分片根名，值 = 文件名） |
| 代价 | 分片根若不在顶层，它的父指针会跨文件，单看一个分片时校验可能报 E011；完整读取要连着整个集合一起看 |

### append-v1：单文件修订

**一句话**：不拆文件也能"改一个词只写几十字节"——把改动作为一条**同编号的新记录**追加到文件末尾，读的时候每个编号取最后一条。

**它解决什么**：息壤的节点是变长记录，原地改一个词就要挪动后面所有字节，等于整份重写（实测：179 MB / 347 万节点的文件，改一个词要 20.5 秒）。追加一条记录只要几十字节，毫秒级落盘。

| 项 | 说明 |
|----|------|
| 怎么声明 | 被追加编辑过的那个**根**下挂一个辅助节点 `@protocol = append-v1`（普通名字的根不需要声明；声明放在根下，随文件分发） |
| 怎么写 | 只往文件**末尾追加**一条「同一编号的新记录」（同编号 = 修订，后写覆盖）；新节点 = 新编号的一条记录 |
| 怎么读 | 按文件内追加顺序，**每个编号取最后一条**（折叠视图）；同一个编号的多条记录里，只有最后一条算数 |
| 怎么删 | 删 = 追加一条同编号、名字与值都为空的记录（留空槽位，编号不消失，与 `shard-v1` 一致） |
| 重复编号算不算错 | 声明了 `append-v1` 的根下**不算错**（是修订）；没声明却出现重复编号，仍按 E002「编号冲突」报 |
| 合并 | 追加会越积越多；用 `xr compact <文件>` 把「同一编号只留最后一条」折叠回基版（手动，v1 不自动） |
| 写崩了怎么办 | 追加写到一半留下的半条记录 = 尾部残片：读取时忽略并提示（F015），写入前先把它截断 |
| 代价 | 同一编号会短暂出现多份，文件比"折叠版"大；不 `compact` 就会一直涨。读取方必须实现"后写覆盖"，老读取器读这种文件会报 E002 或出错 |

### catalog-v1：本机目录

**一句话**：在本机维护一份「编号 → 文件」的目录，用来跨库找节点——在常用词库里看到「猫」，不必先知道它在生物词库，直接由目录定位过去。

**它解决什么**：节点编号（UUID）全局唯一，但引用里只存编号、不存文件名；要跨文件找，就得知道「这个编号在哪个文件」。

| 项 | 说明 |
|----|------|
| 放在哪 | 用户级单个文件，默认 `~/.config/xirang/catalog.idx`；可用环境变量 `XIRANG_CATALOG` 改。它只是缓存，随时可删、可重建 |
| 什么时候写 | 读写命令默认都会顺带维护（读命令可用 `--no-index` 或 `XIRANG_INDEX=off` 关闭）；也可以显式用 `xr catalog scan` 扫描 |
| 怎么写才快 | 「文件段」（路径 + 指纹 + 条数）在前、按编号排好序的条目段在后；查一个编号用**磁盘二分**，只读十几条小记录，不把整个目录读进内存 |
| 怎么判过期 | 每条记录带文件的尺寸与修改时间，对不上就重扫该文件；写入用「临时文件 + 改名」原子替换，失败静默（不影响命令） |
| 同一个编号在多个文件 | **不是冲突**，是正常现象：常用词库和生物词库各留一份自己的「猫」，各挂自己关心的孩子；查一个编号会拿到**所有**含它的文件 |
| 读时取并集 | 按编号读节点时，把孩子跨**相关文件**凑成并集（相关文件 = 命令行给的文件 + 目录里含该编号的文件）；顺序固定为「文件顺序 + 文件内追加序」，同一孩子编号只算一次（来源取最先出现的文件） |
| 来源只在内存 | 每条结果带一个「来自哪个文件」的来源标记，只活在读取现场；不写进 `.xirang`，内核与保存 / 导出都不多这个字段 |
| 什么时候要人裁决 | 只有**同一个编号、节点自身（名字 / 值）不一样**时才需要裁决：`xr catalog check` 列出这些编号（连同两边各自的孩子作为判断依据），`xr catalog check --sync <编号> --base <文件>` 把别处该节点的名字 / 值改成与基准一致（**孩子一律不动**） |
| 代价 | 目录会随「读过的文件」累积；它属于本机、跨项目，不随数据文件分发 |

### XRIDX：侧车索引（实现层缓存）

**一句话**：在每个 `.xirang` 旁边放一份小索引（`<文件>.xirang.idx`），记录「每个节点在第几个字节」，让读取直接跳过去，不用从头扫。

| 项 | 说明 |
|----|------|
| 它解决什么 | 文件里的节点是一个接一个顺序堆放的，没有现成目录；想直接跳到某个节点，就得先记下它在文件里的位置 |
| 里面有什么 | 四个基础块：根块（根编号 → 偏移 + 长度）、归属块（节点编号 → 所属根）、反向块（谁引用了我）、父子块（父编号 → 孩子编号 + 偏移 + 长度）；四块都按编号排序，用磁盘二分查找。末尾还有**修订块**（`append-v1` 追加的历史记录，按写入顺序） |
| 怎么增量 | 索引头记着「已经扫到源文件第几字节」；文件只变长时，**只扫新增的那一段**并往修订块追加条目，不重建整张索引（实测：179 MB 文件的索引重建要 15.6 秒，增量补扫是毫秒级）。读取时修订块先于基础块命中，实现"后写覆盖" |
| 什么时候失效 | 源文件尺寸回退、或被从中间改写（前缀校验对不上）→ 整份重建；解码后发现编号对不上也会重建。它只是缓存，删掉会自动重建 |

### wsidx-v1：工作区统一索引（三本台账）

**一句话**：每个工作区一套索引，放在 `<工作区>/.xirang-index/`，三本台账（定位 / 关系 / 反向）各自回答一类问题，写入只追加日志、压实才合并。

| 项 | 说明 |
|----|------|
| 放在哪 | 工作区根目录下的隐藏目录（默认 = 数据文件所在目录，可用 `XIRANG_WORKSPACE` 指定更大范围）。用户不必看见；可整体删除、可重建 |
| 三本台账 | 定位本（编号 → 文件 + 偏移 + 长度 + 树根，按编号排序）；关系本（树根 + 父 → 孩子 + 位置，按「树根 + 父」排序，同一棵树连续存放）；反向本（被引用编号 → 来源编号 + 文件） |
| 怎么分块 | 每本按条目数分块（默认每块 100 万条），块内定长、按各自的首键升序；块边界与文件表记在 `index.manifest`，常驻内存 |
| 怎么写 | 数据文件落盘后**只追加**日志记录（不原地改块）。每个文件带一个「代号」，判定规则只有一条：**条目属于「写它时那条文件记录」的代号**。整份登记 → 代号 +1，该文件旧代号的条目一律作废；**只追加登记 → 代号一个字都不动**（旧记录的字节位置没挪动，旧条目继续有效），只把变化的那几条作为「后写覆盖」追加进日志；改掉引用还要给旧的那条反向边补一条**墓碑**，否则「谁引用我」会一直列出已经不指向我的节点 |
| 怎么压实 | `xr index compact`：**扫描与建块不持锁**（写者照常写）→ 只在「换 manifest + 清日志」的瞬间持锁。块文件带代数前缀（`loc-g<代数>-0000.blk`）：新块写新名字 → 原子换 manifest → 再删旧代数，**中断在任何时刻都不会出现半新半旧的索引**。扫描期间若有文件被改动，本轮整体放弃、下次重试 |
| 什么时候自动整理 | 读命令（`ws` / `catalog check`）与写命令结束后，若「日志 > 主干 30% 且主干 ≥ 1MB」，CLI 分离一个后台进程执行 `xr index compact`（先给结果、再整理；`XIRANG_INDEX_MAINTENANCE=off` 关闭）；常驻的 MCP / 桌面版用后台线程做同一件事 |
| 怎么判过期 | 每个文件在台账里带指纹（尺寸 + 修改时间）；对不上时该文件的条目一律作废，读路径回退到「整份载入」并提示。「只追加登记」还记着「上次登记到的文件长度 + 那段之前 64 字节的哈希」：长度一点不变也可能被从中间改写，只比长度会静默错位——哈希对不上就退回整份登记 |
| 向前兼容 | **未知段与未知记录类型必须按长度跳过**——以后加字段倒排等新段不必升主版本 |
| 格式版本 | 每个索引文件头带一个格式版本字节（当前 **2**；2026-09 起：文件记录多了「上次登记到的长度 + 前缀守护哈希」、反向本多了墓碑记录）。**版本对不上直接报 F013**，读路径回退整份载入并提示，`xr index rebuild` 重建即可——台账只是缓存，**绝不把新格式当旧格式读** |
| 与 catalog 的分工 | catalog 是账号级的「编号 → 文件」入口（跨工作区）；wsidx 是工作区内的细定位。两者都是缓存，都可删可重建 |
| 代价 | 体积约等于数据的 1.2–2 倍（三本台账之和）；**改一个词只追加几十到几百字节**（毫秒级），代价是同一编号会攒下多份记录，偶尔要用 `xr compact <文件>` 折叠；整份写入（压实、物理删除）才需要重扫该文件的全部条目 |

## 内核边界

- 内核**只增不改**：节点四属性、7 大类标记永不复用。
- 协议**可扩展**：协议只改变「树怎么组织、怎么存」，不改节点本身。
