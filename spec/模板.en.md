# Template

> [中文版](模板.md)

> **In one line**: a Template is a tree whose shape is fixed once and can be reused. The kernel only says what a node looks like; how you arrange nodes into a tree is up to you.
> **Who it's for**: people who want to keep sets of data in XiRang. This document is a demo of the Template layer, not a hard rule.

XiRang's kernel only covers the "node" — four fields + 7 value types (see [README](https://github.com/outnever/XiRang/blob/main/README.en.md)); that part is a hard constraint, enforced by the validator ([tools/validator.py](https://github.com/outnever/XiRang/blob/main/tools/validator.py)).

Every node carries a "parent" field (16-byte UUID, all zeros = root). Through parent, nodes naturally chain into a hierarchy, which is a "tree". The simplest tree needs only two nodes: a root and a child.

```
Parent
└─ Child
```

A "tree" is the one natural way of organization given by the kernel, and it has no fixed shape of its own — how you lay it out is up to you.

In practice, a lot of data comes in repeated sets: an entry, a record, a kind of configuration. Rather than rebuild the same shape every time, you fix that shape once and reuse it. Such a "tree with a fixed shape, reused over and over" is a **Template**.

A Template is not a hard constraint; design it for your own use. This document is the official demo of the Template layer, for reference only.

## Character legend

This document draws trees with characters; the reading conventions:

```
`→` = reference edge; `←` = "read as" (explains the character on its left)

name = value           ← name: node name; value: node value (text / integer / float / boolean)
└─ child name          ← └─: parent-child edge; child name: the child's node name (child indented under parent)

name                   ← name: node name; node value is empty (empty, type 0)

(empty node)           ← empty name + empty value (ID kept); the slot left by a "delete"

name → target          ← name: node name; target: the node name the reference points to (what is actually stored is the node ID UUID)

@name                  ← @ prefix: auxiliary node convention (not a mandatory format)
```

Node IDs are omitted: the character diagram is a "structure sketch", so node IDs (UUIDs) are not drawn; the implementer generates them when building real nodes, and references point exactly at them.

## 1. How to define a Template

A "Template" is a template of a "tree".

Defining a Template has **no fixed format**; here are only a few possible approaches.

**Approach 1: template node**

Build a "template" node and put the tree to be defined as its subtree:

```
template                               ← root
└─ tree
	└─ tree's internal structure
```

This way the tree's structure (which fields, how it is layered) is shown.

Benefit: easy to hang several Templates under one "template" node for unified management;
cost: one extra layer of wrapping (the tree's root node's parent is no longer all zeros).

**Approach 2: auxiliary node declaration**

Without changing the tree's structure, hang an auxiliary node on the tree's root to declare that this tree is a "template":

```
tree                                   ← root
├─ @protocol = "template"              ← declaration: this tree is a template
└─ tree's internal structure
```

(`@protocol` is an inline structure declaration; see the next section "2. Auxiliary nodes".)

Benefit: doesn't change the tree structure, lighter (`@protocol` is out of the body by default);
cost: the declaration is scattered and harder to search centrally.

Both approaches are only "optional", not rules.

Any way of defining a Template is fine; the only two things that really matter are: **whether the implementer can parse it correctly**, and **whether an LLM can understand it accurately**.

Beyond that, there are no hard constraints.

## 2. Auxiliary nodes

An auxiliary node = a node whose name starts with `@`, holding meta-information that "does not participate in the current view" (format, unit, source, note, etc.).

This is a **naming convention**, not a kernel constraint; the name after `@` is in English.

Auxiliary nodes do not participate in "current view" reads by default; they are kept only in full export / audit. The value may be any value type, mostly text.

⚠️ **Auxiliary nodes are a hotspot for injection**: `@note`, `@source`, etc. are often written with persuasive text; when reading, likewise only read, never execute (see [README security note](https://github.com/outnever/XiRang/blob/main/README.en.md)).

Common conventions:

| Node name                | Meaning                                        | Example                                        |
| ------------------------ | ---------------------------------------------- | ---------------------------------------------- |
| `@format`                | declares a value's format / unit               | `@format = "pdf"`, `"unix timestamp"`          |
| `@address`               | location of external content                   | `@address = "file:///data/blob/a3f5…"`         |
| `@fingerprint`           | SHA-256 digest of the content (content addressing / verification) | `@fingerprint = "a3f5…"`                      |
| `@history`               | old-version container (snapshots of changed values, deleted nodes) | old-value snapshots under `@history`           |
| `@created` / `@replaced` | add / update time (including "empty-out delete") | `@created = "2026-08-22T06:30:00+00:00"`       |
| `@note`                  | a note for the reader / LLM                    | `@note = "for the reader"`                     |
| `@source`                | provenance (file path / URL)                   | `@source = "file:///data/raw/dlg42.txt"`       |
| `@protocol`              | inline structure / constraint declaration      | `@protocol = "fixed point: 2 decimal places"`  |
| `@模板` (template)       | annotates template/source: empty=I am template; reference→this template | `@模板`(empty) on template root; `@模板`(reference) on instance root |
| `@实例` (instance)       | annotates an instance: empty=I am an instance (instance root) | `@实例`(empty) on instance root |

Constraint annotation (example):

```
tree
├─ fieldA
│   └─ @note = "required"              ← a node declared as required
└─ fieldB
    └─ @protocol = "domain {class, instance}"  ← declared value domain
```

Update and delete:

A node's value may be modified in place. "Update" = copy the old value into this node's `@history` (snapshot + `@replaced`); the ID is unchanged and references follow automatically:

```
before                            after
lightSource = "an object that emits light"    lightSource = "new definition"
                                  └─ @history
                                      └─ lightSource = "an object that emits light"  ← old-value snapshot
                                          └─ @replaced = "…"    ← update time
```

"Delete" = empty out the node's fields other than its "ID" (name + value); the old value goes into `@history` (snapshot + `@replaced`); the node stays in place with its ID kept, so it is an "empty slot":

```
before                            after
lamp                              lamp
└─ lightSource = "an object that emits light"   └─ (empty node)     ← name/value emptied, ID kept
                                  └─ @history
                                      └─ lightSource = "an object that emits light"  ← old-value snapshot
                                          └─ @replaced = "…"    ← empty-out (update) time
```

### Template library and instances (`@模板` and `@实例`, annotation style)

Templates and instances are **identified by annotations on their roots**, **not by containers** — so an instance subtree can be freely attached under any parent node (e.g. a 词性 instance can hang under a node of a 词条 instance):

- **Template definition** = a tree whose root has a `<empty>`-valued `@模板` ("I am a template"). Its **ordinary child nodes** = the template structure.
- **Instance** = a tree whose root has a `<empty>`-valued `@实例` ("I am an instance") plus a `<reference→template root>`-valued `@模板` ("I come from this template"). An instance root can be freely attached under any parent node.

```
词条 (template definition, free root)
└─ @模板 (empty)                      ← I am a template
└─ 词形 / 词频 / 词义 → …             ← template structure

词条 (instance, attachable under any parent)
├─ @实例 (empty)                      ← I am an instance
├─ @模板 → 词条 (reference)            ← I come from this template
├─ 词形 = "火"
├─ 词频 = 7
└─ 词义 → …
   └─ 01
      └─ 词性 (instance of another template, nested under 词义/01)
         ├─ @实例
         └─ @模板 → 词性 template
```

**Two kinds of root nodes**

- **Isolated / free-form root**: no `@模板` / `@实例` annotation — freely placed, no structural constraint.
- **Instance root**: annotated `@实例` — a uniform tree, associated to its template via `@模板`(reference), recognizable no matter how much its structure changes.

**Editing rule**: walk up to the **nearest "marked root"** — a `@模板`(empty) root means protected (template definition); an `@实例` root or anything else means editable. **No exceptions, no containers.**

**Instantiation / batch import from a template**: the template's **ordinary child nodes** = the template "shape". Give each node a value by **name** from a record (e.g. a JSON object) to instantiate one tree (instance root annotated `@实例` + `@模板`(reference)); an instance root can be placed under any parent; missing fields stay empty. Batch = instantiate one tree per record.

Example: record `{"词形":"火","词频":7,"词义":{"释义":"燃烧物","词性":"名词"}}` → instance tree `词条` (`@实例` + `@模板→词条` + `词形=火`, `词频=7`, `词义→释义/词性`).

## 3. Expressing basic structures

Using nodes to express common basic data structures (examples only).

Worth noting: any complex tree of nodes can actually be read with no convention at all and organized into a meaningful structure. The basic-structure expressions in this section are normally only for use by the implementation layer.

### Array (ordered list)

One node hangs a sequence of child nodes; the order = **append order** (append-only, naturally ordered, no index needed).

```
example sentences                    ← array container
├─ "There is a lamp on the nightstand."   ← element 1 (unnamed node)
├─ "The streetlight turns on at dusk."     ← element 2
└─ "The desk lamp is on the desk."         ← element 3
```

### map (key-value pairs)

One node hangs several child nodes; **a child's "node name" = key, "node value" = value**. Each entry is a "named + valued" leaf node. Within a tree, names under the same parent must be unique (otherwise two keys collide and the latter overwrites the former).

```
employee info                          ← map container
├─ name = "Zhang San"                 ← key "name", value "Zhang San" (text)
├─ age = 30                            ← key "age", value 30 (integer)
└─ active = true                       ← key "active", value true (boolean)
```

### Enum (closed / open)

An enum is expressed with an "enum container + value-domain child nodes": the kind (closed / open) is declared with `@protocol`, and the current value uses a reference to point at one of the value-domain children.

**Closed enum** (fixed value domain):

```
part of speech                        ← enum container
├─ @protocol = "closed"               ← declaration: closed (value domain fixed, just these below)
├─ noun                                ← value-domain item
├─ verb
├─ adjective
……
```

**Open enum** (extensible value domain):

```
domain                                ← enum container
├─ @protocol = "open"                 ← declaration: open (more categories may be added)
├─ medicine                            ← category
├─ law
└─ daily
```

Current value = a reference → some child in the value domain (e.g. "part of speech → noun").

Constraints rely on the implementation layer: nodes only record "value domain + type + current value"; constraints such as "the current value must ∈ the value domain" and "a closed enum's value domain is immutable" are checked by the validator (implementation layer), not enforced by the nodes themselves.

### Time

Value = an integer (Unix seconds timestamp, UTC by default) or text (ISO string); the unit / format is declared with `@format`.

```
event
├─ occurredAt = 1704067200
│   └─ @format = "unix timestamp"      ← declares the unit
└─ duration = 3600
    └─ @format = "seconds"
```

### Other common structures

**Set**: container + `@protocol = "set"` declaration; elements = child nodes; "unique and unordered elements" is guaranteed by the validator (the kernel does not enforce unique node names).

```
fruits (set)                          ← set container
├─ @protocol = "set"                  ← declaration: set (unique, unordered elements)
├─ apple                               ← element
├─ banana
└─ orange
```

**Tuple**: an array with fixed positions.

```
coordinates
├─ "3"                                 ← position 1
└─ "4"                                 ← position 2
```

**Queue / stack**: array + `@protocol` declaring the end (FIFO / LIFO).

```
queue
├─ @protocol = "queue"                ← declaration: first in, first out
├─ "task1"
├─ "task2"
└─ "task3"
```

**Fixed-point number**: integer + `@protocol` declaring decimal places.

```
price = 12345
└─ @protocol = "fixed point: 2"       ← 2 decimal places → 123.45
```

**Complex number**: two child nodes for real / imaginary part.

```
complex
├─ real = 3.0
└─ imag = 4.0
```

**Record (struct)**: map (field name = child name) + `@protocol` declaring "record" (field names unique, guaranteed by the validator).

```
user (record)
├─ @protocol = "record"               ← declaration: record (field names unique)
├─ name = "Zhang San"
└─ age = 30
```

**Matrix / tensor**: nested arrays + `@protocol` declaring the shape.

```
matrix
├─ @protocol = "matrix 2×2"           ← declares the shape
├─ row1
│   ├─ 1
│   └─ 2
└─ row2
    ├─ 3
    └─ 4
```

**Regex / rich text**: text / blob + `@format`.

```
rich text
├─ content = <blob>
└─ @format = "html"
```

**Cross-system reference**: text + `@format = "uuid"` (external ID) or reference (in-store node).

```
external entry
├─ value = "550e8400-…"
└─ @format = "uuid"
```

## 4. Expressing graphs

XiRang's nodes can likewise be used to organize various graph structures.

For example everyday flowcharts, dependency graphs, sequence diagrams, and so on.

What must be noted: in graph theory the "vertex" corresponds in XiRang not to **a single node** but to **a subtree**.

Because a vertex usually carries several pieces of data (name, state, attributes…), and those data form a tree.

The graph's "edge" is implemented with a **reference** (vertex A's reference → the subtree root node of vertex B).

So a "graph" = **several subtrees (vertices) + reference edges (edges)**. Reference edges may form cycles (E006 only forbids parent-edge cycles; R001 only checks that a reference target exists, it does not forbid cycles).

### ① State machine (vertices with attributes + cyclic transitions)

```
state: idle                          ← vertex (a subtree)
├─ description = "waiting for a task"   ← attribute
└─ transition
    ├─ task received → state: processing   ← edge (reference → another vertex)
    └─ timeout → state: idle               ← edge (back edge, allowed)

state: processing                    ← vertex
├─ description = "executing"
└─ transition
    ├─ done → state: idle            ← reference
    └─ failed → state: retry         ← reference (cycle)
```

### ② Dependency graph (many-to-many + shared dependencies)

```
packageA
├─ version = "1.0"
└─ dependencies
    ├─ → packageB                    ← reference
    └─ → packageC

packageB
├─ version = "2.0"
└─ dependencies
    └─ → packageC                    ← reference (C shared by A and B)
```

### ③ Flowchart (loop back edge)

```
start
└─ next → decision                   ← reference

decision
└─ branch
    ├─ yes → process                 ← reference
    └─ no → end                      ← reference

process
└─ done → decision                   ← reference (loop back edge)
```

## 5. Use cases

### Writing (events / person relations)

```
Zhang San (person)                   ← root
├─ name = "Zhang San"
└─ residence → Beijing               ← reference

event-2024-001                       ← root
├─ subject → Zhang San               ← reference (who)
├─ location → Beijing                ← reference (where)
├─ time = 1715328000
│   └─ @format = "unix timestamp"     ← annotate parse format
└─ cause → event-2023-999            ← reference (causal edge, may cycle)
```

### Memory (declarative memory)

Similar to "event", plus a "provenance" (`@source`):

```
event-2024-001 (memory)              ← root
├─ subject → Zhang San               ← reference
├─ time = 1715328000
│   └─ @format = "unix timestamp"     ← annotate parse format
├─ description = "Zhang San went to Beijing"  ← text
└─ @source = "file:///data/raw/dlg42.txt"     ← provenance (file path / URL)
```

### Lexicon (entries)

```
lamp                                 ← root
├─ wordForm = "lamp"
├─ frequency = 2046
└─ sense
    └─ 01
        ├─ definition = "an object that emits light for illumination or other uses"
        └─ partOfSpeech
            └─ noun
                ├─ hierarchyLevel = "class"
                └─ parentClass → lightSource        ← reference
```

## 6. Format conversion

XiRang ↔ other formats (JSON / XML / YAML lossless round-trip; Markdown lossy, export only). Reference implementation [tools/convert.py](https://github.com/outnever/XiRang/blob/main/tools/convert.py).

A few key distinctions when converting:

- **Value that is an object (nested) → subtree**: a JSON nested object becomes child nodes (parent edges).
- **Cross-object reference → reference edge**: a JSON reference "pointing at another object" becomes a XiRang "reference".
- **Empty object `{}` → empty type**: an empty object is a "container", corresponding to an empty-type node (not empty text); an empty string `""` is empty text.

### Example: JSON → node tree

```json
{
  "lightSource": { "definition": "an object that emits light" },
  "lamp": {
    "wordForm": "lamp",
    "sense": { "definition": "lighting apparatus" },
    "note": {},
    "parentClass": "lightSource"
  }
}
```

```
lightSource                          ← root
└─ definition = "an object that emits light"

lamp                                 ← root
├─ wordForm = "lamp"
├─ sense                              ← subtree (nested object)
│   └─ definition = "lighting apparatus"
├─ note                               ← empty-type container (empty object {})
└─ parentClass → lightSource          ← reference (cross-object)
```

### Example: node tree → JSON (lossless vs lossy)

This uses the node tree converted from the "JSON → node tree" JSON content above.

Lossless export means lossless export **for the XiRang nodes**, not lossless export for the JSON format.

Each node is saved as one JSON object, fully preserving node ID, parent ID, and value type.

```json
{
  "format": "xirang", "kernel": "1.0",
  "nodes": [
    {"id": "…0000", "parent": null,   "name": "lightSource", "value": {"type": "text", "value": "an object that emits light"}},
    {"id": "…0001", "parent": null,   "name": "lamp",        "value": {"type": "empty", "value": null}},
    {"id": "…0002", "parent": "…0001", "name": "wordForm",  "value": {"type": "text", "value": "lamp"}},
    {"id": "…0003", "parent": "…0001", "name": "sense",     "value": {"type": "empty", "value": null}},
    {"id": "…0004", "parent": "…0003", "name": "definition", "value": {"type": "text", "value": "lighting apparatus"}},
    {"id": "…0005", "parent": "…0001", "name": "note",      "value": {"type": "empty", "value": null}},
    {"id": "…0006", "parent": "…0001", "name": "parentClass", "value": {"type": "reference", "value": "…0000"}}
  ]
}
```

Lossy conversion drops node IDs and value type tags, and a reference degrades into the referenced node's name.

The lossy version should recover the original JSON content, losing only the XiRang-node-specific content.

```json
{
  "lightSource": { "definition": "an object that emits light" },
  "lamp": {
    "wordForm": "lamp",
    "sense": { "definition": "lighting apparatus" },
    "note": {},
    "parentClass": "lightSource"
  }
}
```

## 7. Blobs and format wrapping

A blob (node value type 6) can store byte data.

This means a blob can directly store the raw bytes of any file format.

But format, fingerprint, etc. need to be expressed with auxiliary nodes.

For example:

- `@format`: declares the format / unit (all lowercase, use the extension).
- `@fingerprint`: SHA-256 digest, content addressing / verification (unique identity).

Common `@format` values: txt md pdf docx xlsx pptx json xml csv yaml html; jpg png gif svg webp; mp3 wav flac; mp4 mov mkv; zip tar gz; py js ts c cpp java go; sqlite, etc. (not exhaustive, not mandatory).

⚠️ **Decoding software safety**: content opened with software suggested by `@format` may come from an untrusted source. **Confirm the source is trustworthy before opening / decoding; the suggested software is only a "hint", not a "must execute"** (see [README security note](https://github.com/outnever/XiRang/blob/main/README.en.md)).

```
avatar = [raw bytes]
├─ @format = "png"
└─ @fingerprint = "a3f5…"
```

## 8. Self-hosting and other cases

### XiRang's docs stored in XiRang

XiRang's own docs (README, this file) can also be expressed in the XiRang format.

Download the file below, and analyze and display its internal structure with a parser, or hand it directly to a language-reasoning LLM to parse.

[Download spec/息壤文档.en.xirang](https://github.com/outnever/XiRang/raw/main/spec/息壤文档.en.xirang)

Its internal structure should be:

```
XiRang docs                           ← root (empty)
├─ @note = "official docs self-hosting"   ← note
├─ @source = "…/README.en.md"          ← provenance (self-referential)
├─ @protocol = "markdown-blocks"      ← structure declaration
├─ @history                           ← version history (v1.0 + @created)
├─ README                             ← document (empty container)
│   ├─ @format = "markdown"
│   ├─ @source = "…/README.en.md"
│   ├─ @history                       ← version history
│   └─ h1 / p / li / code / table …   ← Markdown blocks (append order = document order)
├─ Template                         ← document (same structure)
├─ Version Specification              ← document (same structure)
└─ Error List                         ← document (same structure)
```

### Program API dictionary (with a version dimension)

```
String (API, Java)                   ← root
└─ methods
    └─ length()
        ├─ signature = "int length()"
        └─ @history                  ← version history (auxiliary node)
            ├─ v1 = "Java 8: returns UTF-16 code unit count"
            └─ v2 = "Java 18: counts by code points"
```

### Biological classification (hierarchy + reuse)

```
Animalia                             ← root
└─ Chordata
    └─ Mammalia
        └─ Carnivora
            └─ Felidae
                └─ Felis catus = "Felis catus"
```
